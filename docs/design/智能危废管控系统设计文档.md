## 1. 文档说明

### 1.1 编制目的

定义业务域模型、模块关联、权限贯通、**五微服务边界**、完整技术选型，以及多端 APP、部署与监管对接要点。

### 1.2 设计原则

| 原则 | 说明 |
| --- | --- |
| 微服务边界清晰 | 人机入口、设备接入、**业务域**、历史、推送五服务互不越界 |
| 业务集中 | 仓储/物资/盘点/运输/告警/围栏/审批/**巡检（本期）**等均在业务服务 |
| 职责任分离 | Portal 只读；Admin 管人管权管主数据；APP 现场执行 + 态势查看 |
| 权限贯通 | 用户鉴权在 WebHTTP（JWT + Casbin）；服务间 **mTLS** |
| 合规优先 | 转移联单、台账、证据链、审批留痕 |
| 一物一码 | 贯穿入库→在库→在途→签收 |
| 单仓部署 | 本期一套实例服务一个仓体（Scope 仍保留扩展能力） |
| 多端一致 | Flutter 覆盖 Android / iOS；实时 Protobuf |
| 可追溯 | 人员、权限、单据、扫码、告警、轨迹、审批全量审计 |

### 1.3 术语

| 术语 | 含义 |
| --- | --- |
| Portal / Admin / APP | 网页前台 / 网页后台 / 管控 APP |
| WebHTTP | Gin 对外 REST + IAM；薄 BFF，业务委托业务服务 |
| MQTT 接入 | 仅外部设备接入（EMQX） |
| **业务服务** | 全部领域业务（含告警、围栏计算、多级审批、**巡检**） |
| 历史服务 | 遥测/轨迹/告警等历史持久化与查询 |
| 推送服务 | 告警与外部数据 → Protobuf 二进制下行 |
| 权限点 | `资源:动作`，如 `outbound:confirm` |
| Canonical | MQTT 归一内部模型 |
| PushEnvelope | 推送 Protobuf 信封 |
| 内部总线 | **NSQ** |

## 2. 业务域与模块关联总览

### 2.1 核心业务对象（枢纽）

```
┌─────────────┐     生成/绑定      ┌─────────────┐
│  仓储单据    │ ────────────────► │   唯一码     │
└──────┬──────┘                   └──────┬──────┘
       ▼                                  ▼
┌─────────────┐     装载/轨迹      ┌─────────────┐
│  运输任务    │ ◄───────────────► │  运输单元    │
└──────┬──────┘                   └──────┬──────┘
       ▼                                  ▼
┌─────────────┐     超阈/越界      ┌─────────────┐
│  告警事件    │ ◄─────────────── │ 监测/围栏    │
└─────────────┘                   └─────────────┘
         ▲ 均由「业务服务」写状态机与账务
```

| 枢纽对象 | 生命周期 | 主要关联 |
| --- | --- | --- |
| 唯一码 | 已发放→在库→在途→已签收（可作废） | 仓储、物资、盘点、运输、台账 |
| 仓储单据 | 草稿→已开单→执行中→已完成/作废 | 库存、运输、联单 |
| 运输任务 | 待发→在途→已签收 | 出库单、单元、打卡、围栏 |
| 告警事件 | 触发→待确认→已确认/已关闭 | 阈值、监测、围栏、通知 |
| 审批单 | 待审→逐级审批中→通过/驳回（**级数可配**） | 库存调整等受控写操作 |
| 巡检任务（**本期**） | 待执行→执行中→已完成 | 点位、照片、异常转告警 |

### 2.2 功能模块依赖（业务服务内聚）

```
                    ┌──────────────────┐
                    │ WebHTTP: IAM/Casbin│  ← 用户请求入口与鉴权
                    └────────┬─────────┘
                             │ gRPC (mTLS)
                    ┌────────▼─────────┐
                    │   业务服务 svc-biz │
                    │ 仓储·物资·盘点·运输 │
                    │ 告警·围栏·审批·巡检│
                    └────────┬─────────┘
         ┌───────────────────┼───────────────────┐
         ▼                   ▼                   ▼
    历史服务              推送服务              MySQL
    svc-history           svc-push            业务主库
         ▲                   ▲
         └───────── NSQ ←────┘
                      ▲
                 MQTT 接入 ←── EMQX ←── 外部设备
```

**依赖规则**：

1. 无 WebHTTP 鉴权上下文，不对用户暴露业务写接口。
2. 库存变更只来自：入库确认、出库确认、盘点过账、**经审批通过**的库存调整。
3. 运输打卡须绑定有效任务；**签收执行权限为 `outbound:confirm`**。
4. 告警与围栏计算仅在业务服务产生；人工只能确认/关闭。
5. 台账/联单只消费已生效业务事件。

### 2.3 跨模块主流程

#### A. 入库

```
Admin → WebHTTP → 业务服务：开单发码
APP → WebHTTP → 业务服务：inbound:confirm 扫码上架
→ 库存+ / 事件 → 历史(可选) / Portal 刷新
```

#### B. 出库 + 运输 + 签收

```
Admin → 业务服务：出库开单、创建运输任务
APP → checkin:exec 打卡（在途）
APP → outbound:confirm 签收确认 → 唯一码=已签收、库存-
```

#### C. 盘点

```
Admin 建任务 → APP inventory:scan → Admin inventory:adjust（可配审批）→ 报表
```

#### D. 监测告警

```
设备 → EMQX → svc-mqtt → Canonical → NSQ
  → history 落库
  → biz 阈值/围栏计算 → 告警事件
  → push Protobuf（实时）+ 厂商推送（摘要）
用户 ack → WebHTTP → biz
```

#### E. 库存调整（强制审批）

```
申请人 Admin 提交调整单 → 业务服务建审批单
审批人通过 → 才写库存账 → 审计
驳回 → 不改库存
```

#### E'. 多级审批（可配）

```
Admin 配置审批模板（级数 N、每级角色/人员）
申请人提交（如库存调整）→ 生成审批单 level=1..N
第 k 级 approval:act 通过 → 进入 k+1；驳回则终止且不改库存
全部通过 → 业务服务执行写库存等副作用 → 审计
```

#### F. 巡检（本期）

```
Admin 建巡检计划/路线/任务 → APP inspection:exec 到点打卡拍照
→ 业务服务归档；异常可自动/手动转告警
权限：inspection:view / inspection:create / inspection:exec
```

### 2.4 模块 ↔ 数据归属

| 模块 | 主写 | 服务 |
| --- | --- | --- |
| 人员权限 | users, roles, casbin_rules, scopes | WebHTTP（IAM） |
| 仓储/物资/盘点/运输/审批/巡检/告警/围栏配置 | 业务表 | **业务服务** |
| 遥测/轨迹/告警历史 | 时序与历史表 | 历史服务 |
| 对象（照片/附件） | Bucket 对象键 | 对象存储；业务表存元数据 |
| Schema/设备绑定配置 | 配置表 | 业务服务写；mqtt 热加载 |

## 3. 人员管理与权限架构

### 3.1 模型

```
User ──N:N── Role ── Casbin 策略 ── Permission
  ├── ClientAccess: portal | admin | app
  └── Scope: warehouse_ids（单仓部署下通常为当前仓）
```

**三重校验**：L1 端访问 × L2 Casbin 权限点 × L3 数据范围。

### 3.2 权限点总表（按模块）

| 模块 | 权限点 | 主要端 |
| --- | --- | --- |
| 门户 | `portal:access` `admin:access` `app:access` | 各端 |
| 人员 | `user:view/edit` `role:view/edit` `audit:view` | Admin |
| 仓储 | `warehouse:view` `inbound:edit` `inbound:confirm` `outbound:edit` `outbound:confirm` `code:issue` | Admin/APP |
| 物资 | `material:view/edit/export` `stock:adjust` | 三端/Admin |
| 审批 | `approval:view` `approval:act` | Admin |
| 盘点 | `inventory:view/create/scan/adjust` | Admin/APP |
| 告警 | `alarm:view` `alarm:ack` `threshold:edit` | 三端/Admin |
| 运输 | `transport:view/edit` `unit:edit` `checkin:exec` `track:view` | Admin/APP |
| 围栏 | `geofence:view/edit` | 三端/Admin |
| 监测 | `monitor:view` `device:edit` | 三端/Admin |
| MQTT | `mqtt:schema:edit` | Admin |
| 对接 | `openapi:config` | Admin |
| 巡检 | `inspection:view/create/exec` | Admin/APP |

**签收定论**：到达签收使用 **`outbound:confirm`**（不再用 `checkin:exec` 兼签收）。

### 3.3 预置角色（摘要）

| 角色 | 要点 |
| --- | --- |
| 系统管理员 | 全权含角色、对接、Schema |
| 业务管理员 | 开单/任务/配置；无改权限体系；可审批 |
| 安全员 | 阈值/围栏/告警处置 |
| 仓管员 | 开单、盘点、入出库确认 |
| 驾驶员 | APP + 打卡；无签收则不授 `outbound:confirm` |
| 只读观察员 | Portal/APP 只读 |
| 审批人 | `approval:act`（可按级配置不同角色） |
| 巡检员 | `app:access` + `inspection:exec` + 必要只读 |

### 3.4 Token 与登录

| 项 | 定论 |
| --- | --- |
| Token | **Access JWT + Refresh Token** |
| Access TTL | **30 分钟** |
| Refresh TTL | **7 天**（配套默认；可在 etcd 调整） |
| 首次登录 | **强制改密** |
| 企业身份 | **LDAP only**（本地账号并存；不做 OIDC/CAS） |
| 授权引擎 | **Casbin** |
| 停用账号 | 拒绝新 Access；Refresh 黑名单/版本号失效 |

登录响应下发：`accessToken`、`refreshToken`、`permissions`、`scopes`、`clients`、`pushEndpoint`、`mustChangePassword`。

### 3.5 Gin 鉴权链（WebHTTP）

```
Request → Recovery → RequestID → AuthJWT
  → Casbin Enforce(sub, obj, act)  // L2
  → RequireClient / Scope          // L1 / L3
  → Handler → gRPC(mTLS) → 业务服务 / 历史服务
  → Audit
```

客户端只做菜单裁剪；服务端强制校验。

## 5. 微服务技术架构（Go · monorepo）

### 5.1 服务一览与边界

| 服务 | 进程 | 对谁 | 职责 | 禁止 |
| --- | --- | --- | --- | --- |
| **WebHTTP** | `svc-webhttp` | 三端 | Gin REST、JWT+Casbin、**LDAP**、WSS 鉴权反代、聚合查询 | 直连 EMQX；不落业务核心事务（委托 biz） |
| **MQTT** | `svc-mqtt` | 仅设备 | EMQX 消费、Schema→Canonical、NSQ 发布；指令下行 | 业务 HTTP；长期历史；告警判定 |
| **业务服务** | `svc-biz` | 内部 | **全部领域业务**：仓储/物资/盘点/运输/告警/围栏/多级审批/台账出站/**巡检** | 对浏览器直接暴露；接 MQTT Broker |
| **历史** | `svc-history` | 内部 | 遥测/轨迹/告警历史；**纯 MySQL 分区表**；保留周期可配 | 规则；推送；业务写库存 |
| **推送** | `svc-push` | 经反代的 WSS、APNs/厂商 | Canonical/告警 → Protobuf；通知栏**仅摘要** | 写业务主库；接设备 MQTT |

> **人机 → WebHTTP；设备 → MQTT；业务状态 → Biz；历史 → History；实时二进制 → Push。**

### 5.2 逻辑架构

```
                 Portal / Admin / Flutter APP
                  │ HTTPS JSON              │ WSS (Nginx→WebHTTP 鉴权→反代 Push)
                  ▼                         ▼
           ┌─────────────┐           ┌─────────────┐
           │ svc-webhttp │──升级───►│  svc-push   │
           │ Gin Casbin  │           │ Protobuf    │
           └──────┬──────┘           └──────▲──────┘
                  │ mTLS gRPC                │
           ┌──────▼──────┐                   │
           │  svc-biz    │────── NSQ ────────┤
           │ MySQL·GORM  │                   │
           └──────▲──────┘            ┌──────┴──────┐
                  │                   │ svc-history │
                  │ NSQ               │ 历史库可配保留 │
           ┌──────┴──────┐            └─────────────┘
           │  svc-mqtt   │◄── MQTTS ── EMQX ◄── 设备
           └─────────────┘
                  │
            etcd 配置 · Vault/K8s Secret · Redis · 对象存储
```

### 5.3 端到端数据流

**设备数据**

```
设备(一机一证/账密) → EMQX → svc-mqtt → Canonical → NSQ
  → history / biz(告警+围栏) / push(Protobuf)
```

**人机业务**

```
三端 → WebHTTP(鉴权) → gRPC → svc-biz（事务 + 审批 + 事件）
查曲线/轨迹 → WebHTTP → history
实时 → WebHTTP 鉴权后反代 → push
```

**告警确认**

```
ack API → WebHTTP → biz → NSQ alarm.acked → push/history
```

### 5.4 各服务要点

#### 5.4.1 WebHTTP（Gin）

- 中间件：JWT（Access）+ Casbin + Client + Scope。
- Refresh 接口轮换 Refresh Token。
- **LDAP only**：绑定成功后关联/创建本地用户并签发 Access(30min)+Refresh(7d)。
- 业务 Handler **不直接写核心领域表**，一律 gRPC 调 `svc-biz`。
- WSS：校验 JWT 与权限后，**反向代理升级**到 `svc-push`。
- IAM 用户/角色/Casbin 策略可落 WebHTTP 库或共享 MySQL（逻辑归属 IAM）。

#### 5.4.2 MQTT 接入

- 唯一设备接触面；Schema 配置来自 biz/etcd，NSQ `config.mqtt.updated` 热加载。
- 设备认证：**一机一证（推荐）** + 支持用户名密码（EMQX ACL）。
- 短期去重用 Redis；长期数据交 history。

#### 5.4.3 业务服务（原告警服务扩展）

| 域 | 能力 |
| --- | --- |
| 仓储物资 | 开单、发码、入出库确认、库存账、**库存调整审批流** |
| 盘点运输 | 任务、扫码实盘、打卡、**签收 outbound:confirm** |
| 告警围栏 | 阈值规则、**围栏计算**、告警状态机 |
| 配置 | 阈值/围栏/设备元数据/Schema 配置写入；发 NSQ 通知 |
| 审批 | **多级可配**审批引擎（库存调整优先；模板可复用） |
| 巡检 | 计划、路线、任务、APP 执行记录、异常转告警（**本期**） |
| 监管出站 | OpenAPI/SFTP Outbox（见 §11） |

- ORM：**GORM** + **MySQL**。
- 对内 gRPC；无用户 JWT，靠 **mTLS** 服务身份。
- 围栏计算：**在本服务内**对定位 Canonical 评估，产生越界告警事件。

**多级审批模型（摘要）**：

| 概念 | 说明 |
| --- | --- |
| 审批模板 | 绑定业务类型（如 `stock_adjust`）；级数 N≥1 可配 |
| 审批节点 | 每级指定角色和/或人员；通过策略：任一人 / 全部（可配） |
| 审批单 | 实例；当前级、状态、意见、时间；全程审计 |
| 副作用 | **仅终态通过后**由领域命令执行（如改库存） |

#### 5.4.4 历史服务

- 消费 NSQ 写入历史；存储为 **纯 MySQL 分区表**（按时间 RANGE 分区等），不引入独立时序库。
- **热/温/冷保留与分区清理策略全部可配**（etcd）。
- gRPC 查询供 WebHTTP 聚合。

#### 5.4.5 推送服务

- 输入：NSQ `iot.canonical.*`、`alarm.*`。
- 输出：PushEnvelope Protobuf（WSS binary）；APNs / 各 Android 厂商通道。
- **通知栏只放摘要**（标题/级别/仓/时间）；详情经 REST 拉告警/监测。
- 连接来自 Nginx→WebHTTP 鉴权反代，不暴露裸 Push 端口给公网（按部署可调）。

### 5.5 PushEnvelope（Protobuf）

| 字段 | 说明 |
| --- | --- |
| `ver` / `msg_type` / `msg_id` / `ts_unix_ms` | 版本、类型、幂等、时间 |
| `warehouse_id` / `device_id` | 路由 |
| `payload` oneof | Telemetry / Location / DeviceEvent / Alarm（摘要字段） |

WSS 仅 binary Proto；客户端与 `api/proto/push/v1` 共用。

### 5.6 NSQ 事件（节选）

| Topic | 发布 | 消费 |
| --- | --- | --- |
| `iot.canonical.v1` | mqtt | history, biz, push |
| `iot.command.v1` | biz | mqtt |
| `alarm.*` | biz | history, push |
| `config.*` | biz / webhttp | mqtt, biz |
| `biz.*.confirmed` | biz | history, openapi-outbox |

消费幂等：`msg_id` / 业务单号。

## 9. 部署与运行环境

### 9.1 拓扑

- **Nginx**：TLS 终止、`/api`→WebHTTP、`/v1/stream`→WebHTTP（再反代 Push）、静态 Portal/Admin。
- 五服务 + EMQX + NSQ + MySQL + Redis + etcd + **MinIO**。
- 密钥：**Vault** 注入运行环境（Compose `env_file` / Windows 服务环境变量）；不把生产密钥写入仓库。

### 9.2 Linux（主路径）

- **Docker Compose** 编排全部容器（应用 + 中间件）。
- **systemd** 管理 Compose 栈（开机自启、失败重启、统一 journal 日志入口）。
- 提供 `deploy/compose` 与 `deploy/systemd/*.service`。

### 9.3 Windows

- **应用服务与中间件均可部署在 Windows**（一体机/无 Linux 机房场景）。
- 应用：Windows Service 或 Windows 容器；中间件选用 Windows 兼容发行版/容器（MySQL、Redis、NSQ、EMQX、etcd、MinIO、Nginx 等按官方 Windows 支持矩阵安装）。
- 提供 `deploy/windows` 安装脚本与服务注册说明；与 Linux Compose 配置项对齐，降低双平台漂移。

### 9.4 单仓

一套环境对应一个暂存仓；配置中 `warehouse_id` 默认唯一；权限 Scope 仍按仓字段预留。

## 11. 监管对接方案

采用 **双通道 + Outbox**，在业务服务内实现出站：

| 通道 | 用途 | 说明 |
| --- | --- | --- |
| **OpenAPI（HTTPS）** | 准实时 | 台账、库存快照、告警、联单绑定查询/推送；鉴权用监管方颁发的客户端凭证 |
| **SFTP 文件交换** | 批量/日终 | CSV/XML 按省平台模板投递；适合弱实时 |

**可靠投递**：

1. 业务事务提交时写 `openapi_outbox` / `sftp_outbox`（同一 MySQL 事务）。
2. Worker 扫描 Outbox → 调用/上传 → 成功标记；失败重试与死信告警。
3. Admin `openapi:config` 配置开关、地址、映射、证书。
4. 全链路保留投递日志供抽查。

省平台字段差异用映射表配置，避免改代码。
