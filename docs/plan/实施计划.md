## 0. 总览

```
阶段 A 后端完善与服务拆分     ████████░░░░  约 6～8 周（视人力）
阶段 B Web 前端（Portal+Admin）  ██████░░░░░░  约 3～4 周（可与 A 后半并行接口联调）
阶段 C Flutter APP               █████░░░░░░░  约 3～4 周（依赖 A 现场执行 API 稳定）
阶段 D 联调·验收·上线验证        ███░░░░░░░░░  约 2 周
```

**原则**

1. **后端先行**：状态机、库存口径、权限点、OpenAPI 契约先冻结，再铺页面。
2. **契约驱动**：每完成一组 API 即更新 OpenAPI / 示例请求；前端与 APP 只消费契约。
3. **垂直切片**：优先打通「入库→在库→出库锁定→运输打卡→签收」主链路，再扩告警/巡检/监管。
4. **同进程可先用**：业务逻辑先在 `backend/internal/biz` 完善；稳定后再拆 gRPC 进程，避免过早分布式调试。

## 5. 并行与依赖关系（简图）

```
A1 契约 ──┬──► A2 业务 API ──┬──► A3 IoT/推送 ──► A4 拆分部署
          │                 │
          │                 ├──► B2 Admin 业务页
          └──► B1 前端壳 ───┤
                            └──► B3 Portal（等 A3 更佳）

A2 执行 API 稳定 ──► C1 APP壳 ──► C2 执行 ──► C3 展示推送

A4 + B3 + C3 就绪 ──► D 验证
```

允许的并行：

- **B1** 可在 A1 完成后立即开始（不等 A2 全部结束）。  
- **B2** 按模块跟随 A2 子项交付，避免前端空等。  
- **C1** 可在 A2.1～A2.3 接口冻结后启动。  
- **不建议**在 A2 主链路未通时开始 C2 大规模扫码页。

## 7. 风险与缓冲

| 风险 | 缓解 |
| --- | --- |
| 过早拆微服务拖慢联调 | A2 完成前保持 biz 同进程或本地 gRPC |
| 百度地图/推送证书耗时 | C3/B3 可先 Mock 地图与本地通知 |
| LDAP 环境不具备 | 配置开关；测试环境继续本地账号 |
| Windows 中间件兼容 | D2 单列冒烟；生产优先 Linux Compose |
| 需求蔓延（监管字段） | 监管 Outbox 先骨架，字段映射配置化 |
